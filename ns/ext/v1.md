## Purpose

OpenRiC commits never to mint new terms in the ICA RiC-O namespace. This extension namespace holds 57 terms that OpenRiC implementations need but RiC-O 1.1 does not define. They fall into three categories:

1. **Response-envelope classes** for paginated JSON-LD list endpoints (e.g. `openricx:RecordList`, `openricx:AgentList`). These are protocol concerns, not archival semantics, and would not normally be upstream candidates.
2. **Pragmatic API shortcuts** that have a clean canonical RDF expansion in RiC-O 1.1 (e.g. `openricx:hasOccupation` → SKOS Concept of `rico:OccupationType`; `openricx:DateRange` → native RiC-O Date pattern). These are kept for API ergonomics.
3. **Candidate upstream proposals** for ICA-EGAD — terms with genuine archival semantics that RiC-O 1.1 does not yet model (e.g. `openricx:ContactPoint`, `openricx:hasAppraisalInformation`, `openricx:containsPersonalData`).

The full per-term disposition with confidence flags is in the [audit document](/audit/ric-o-1.1-audit.html).

### Semantic extension (7)

| Term | Comment |
|---|---|
| `openricx:Function` | ISDF business/archival function. Interim canonical class; see [mapping.md §6.4](/spec/mapping.html). |
| `openricx:ContactPoint` | Repository / organisation contact (address, phone, email). Open candidate-upstream. |
| `openricx:DateRange` | Structured date range (begin / end / expressedDate qualifier). RiC-O 1.1 dropped its own DateRange class. A subclass of `rico:Date` since v0.50.0: literal endpoints on `rico:beginningDate` / `rico:endDate`, type on `rico:hasDateType` → a [date-type concept](/vocab/date-type.html). |
| `openricx:DateRangeSet` | Collection of openricx:DateRange instances. |
| `openricx:Checksum` | Structured checksum (algorithm + value). Optional PREMIS-friendly alternative to inline string form. |
| `openricx:Carrier` | An individual physical medium (this tape, this disc), a subclass of `rico:Thing`. `rico:CarrierType` names only the kind. Pending the Carrier class planned for RiC-O 2.0; added in 1.3.0. |
| `openricx:Occupation` | An occupation an agent held, with its dates; RiC-O 1.1 has only `rico:OccupationType`, the kind. Added in 1.3.0. |

`openricx:hasOccupation`

### Format / carrier / size (6)
`openricx:hasMimeType`, `openricx:mimeType`, `openricx:size`, `openricx:hasPhysicalCharacteristics` (deprecated 2026-10-19; use `rico:physicalCharacteristicsNote`), `openricx:technicalCharacteristics` (RiC-O 1.1's `rico:technicalCharacteristics` applies only to a `rico:Mechanism`), `openricx:productionTechnicalCharacteristics` (deprecated 2026-10-19; use `rico:productionTechnique`)

### Checksum (3)
`openricx:hasChecksum`, `openricx:algorithm`, `openricx:checksumValue`

### Source-standard notes (4, added 2026-10-15)
`openricx:accrualsNote` (ISAD(G) 3.3.3; deprecated, use `rico:accruals`), `openricx:institutionType` (ISDIAH 5.1.5), `openricx:openingHours` (ISDIAH 5.4.1), `openricx:accessibility` (ISDIAH 5.4.3)

### SPARQL endpoint description (4, added 2026-10-15)
`openricx:accessPolicy`, `openricx:rateLimit`, `openricx:maxQueryTimeSeconds`, `openricx:exampleQueriesUrl` - returned by `GET /sparql/info` ([SPARQL Access](/spec/profiles/sparql-access.html), draft)

### Relation qualifiers (1, added in 1.3.0)
`openricx:relationHasAgentRole` - the `rico:RoleType` in which an agent took part in any `rico:Relation`, generalising `rico:creationWithRole` (declared its sub-property). ICA-EGAD intends a generic property for RiC-O 1.2; this one will be bound to it with `owl:equivalentProperty`.

### Kinship of care (6, added in 1.3.0)
`openricx:hasAdoptedChild` (a sub-property of `rico:hasChild`), `openricx:isOrWasAdoptedChildOf`, `openricx:hasFosterChild`, `openricx:isOrWasFosterChildOf`, `openricx:isOrWasGuardianOf`, `openricx:isOrWasUnderGuardianshipOf` - all under `rico:hasFamilyAssociationWith`

### Carrier (2, added in 1.3.0)
`openricx:hasCarrier` (from a `rico:Instantiation` to its `openricx:Carrier`), `openricx:isCarrierOf`

### Rule details (5, added in 1.3.0)
`openricx:restrictionType`, `openricx:customText`, `openricx:appliesToDescendants`, `openricx:securityLevel`, `openricx:securityLevelCode` - on `rico:Rule` nodes for access restrictions and security classifications; a rule's period uses `rico:beginningDate` and `rico:endDate`

### Dates and occupations (2, added in 1.3.0)
`openricx:hasDateOfExistence` (a sub-property of `rico:isAssociatedWithDate`), `openricx:isCurrent` (on an `openricx:Occupation`)

API envelopes, the service description, errors, graph primitives and the `localType`, `jurisdiction` and `role` annotations are in the separate [OpenRiC API vocabulary](/ns/v1.html) (`openric:`).

## Versioning policy

- The `/v1#` namespace path is **stable**. Breaking changes (term removed, semantics changed, domain/range narrowed) MUST happen at `/v2#`.
- Additive changes (new classes, new properties, expanded domain/range, looser constraints) MAY land within `/v1#` and bump the `owl:versionInfo` minor or patch number.
- Every term in `/v1#` is versioned through OpenRiC's [CHANGELOG](https://github.com/openric/spec/blob/main/CHANGELOG.md) and audit doc.
- Term IRIs never carry a version: a term is always `https://openric.org/ns/ext/v1#<name>`, in every release of the ontology. What is versioned is the ontology document. Each release has an `owl:versionIRI` (`https://openric.org/ns/ext/v1.3.0` for this one), which resolves to a page naming that release and its Turtle, and an `owl:priorVersion` pointing at the one before. An implementation that needs to state exactly which definitions it relies on cites the version IRI; it does not change the term IRIs it emits.
- A term RiC-O 1.1 turns out to cover is not removed: it is marked `owl:deprecated true` with `dcterms:isReplacedBy` naming the RiC-O term, and stays valid.
- `https://openric.org/ns/ext/v1` itself returns this HTML page whatever the `Accept` header, because GitHub Pages cannot negotiate content. The Turtle is at [`v1.ttl`](v1.ttl).

## Upstream proposal status

OpenRiC tracks open upstream-proposal candidates against `ICA-EGAD/RiC-O` GitHub issues. Current candidates (April 2026):

- `openricx:ContactPoint` + address fields → propose `rico:ContactPoint` class.
- `openricx:hasAppraisalInformation` → propose `rico:hasAppraisalInformation` (ISAD(G) 3.3.2 backing).
- `openricx:containsPersonalData` → propose `rico:containsPersonalData` (privacy-compliance flag).

The rest are pragmatic API surface and are not expected to migrate upstream.
